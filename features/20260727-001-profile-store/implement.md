- [x] task-001: `list`가 프로필 표를 낸다
  - 목적: `ccswitch list`가 기본 설정 디렉토리 항목과 등록된 프로필을 이름·경로·상태가 붙은
    표로 stdout에 내고, 등록된 프로필이 하나도 없어도 성공으로 끝난다.
  - 접근: 모듈 경로 `github.com/zipkero/ccswitch`, `go` 지시자 1.24로 Go 모듈과 실행 진입점을
    새로 만들고 cobra로 커맨드 트리를 구성한다. 경로 기준값·등록 정보 읽기·디렉토리 상태
    판정은 도메인 경계가 소유하고, 표 출력과 sentinel error → 종료 코드 매핑은 CLI 경계가
    맡는다. 등록 파일이 없는 것은 빈 목록이고, 읽기·파싱 실패나 모르는 `version`은 빈 목록으로
    간주하지 않고 실패로 구분한다.
  - 검증 조건:
    - 결과: 등록이 없는 환경에서 `default` 행만 있는 표가 stdout에 나오고 종료 코드가 0이다.
      등록된 이름은 사전순으로 이어지고, 디렉토리가 없으면 `missing`, 디렉토리가 아닌 것이
      놓였으면 `unusable`로 구별된다. 등록 파일이 손상되었으면 표를 내지 않고 그 파일 경로를
      stderr에 알리며 종료 코드 1로 끝난다. 어느 경우에도 panic이 나지 않고 `list`가 등록이나
      디렉토리를 고쳐 쓰지 않는다.
    - 확인: 임시 디렉토리로 경로 기준값을 만들어 커맨드 트리를 새로 구성하고 출력 스트림을
      값으로 받아 돌리는 테스트로 네 경우(등록 없음 / 정상 / 디렉토리가 밖에서 지워짐 /
      손상된 등록 파일)를 확인한다. 경로 산출 함수는 같은 테스트에서 macOS 스타일 기준값
      (`/Users/me`, `/Users/me/Library/Application Support`)으로도 검증해 Windows에서 실행해도
      통과한다. `go build ./...`, `go vet ./...`, `go test ./...`가 통과한다.
  - 참조: SPEC §5.6, §5.11, §5.12 / ANALYSIS §1, §3, §5 D2, D3, D6, D9, D10, D11, D15

- [x] task-002: `add`가 프로필 디렉토리를 만들고 등록한다
  - 목적: `ccswitch add <name>`이 성공하면 그 이름의 프로필 디렉토리가 홈 아래에 생기고
    등록되어, 이어서 실행한 `list` 출력에 그 이름과 디렉토리 경로가 나타난다.
  - 접근: 이름 검증을 통과한 뒤 등록 정보를 읽고 대상 경로를 조사해, 디렉토리를 먼저 만들고
    등록을 나중에 저장한다. 저장은 같은 디렉토리에 매번 새 이름의 임시 파일을 쓰고 rename으로
    교체하며, 실패 경로에서 임시 파일을 지운다. 디렉토리 경로는 등록에 담지 않고 검증된
    이름과 홈 루트에서 매번 계산한다. 대상 자리에 빈 디렉토리가 이미 있으면 통과시킨다.
  - 검증 조건:
    - 결과: 목적과 동일. 더해서 대상 자리에 빈 디렉토리가 이미 있는 상태에서도 `add`가
      성공하고, 저장이 실패한 경로에서 임시 파일이 남지 않는다.
    - 확인: `add` 직후 디렉토리가 존재하고 `list` 출력에 이름과 경로가 `ok` 상태로 나타나는
      것을 확인하는 테스트. 빈 디렉토리를 미리 만들어 둔 회귀 케이스와, 등록 파일이 저장된 뒤
      다시 읽었을 때 이름이 보존되는 왕복 케이스를 포함한다. 저장 실패를 유도한 뒤 대상
      디렉토리에 임시 파일이 남지 않음을 확인한다.
  - 참조: SPEC §5.1 / ANALYSIS §2, §5 D4, D5, D11, D14

- [x] task-003: `add`가 규칙 위반 이름과 예약 이름을 디스크를 건드리지 않고 거부한다
  - 목적: 이름 규칙에 맞지 않거나 `default`인 이름으로 `add`를 실행하면 프로필이 만들어지지
    않고, 무엇이 잘못되었는지와 허용되는 이름 형식이 stderr에 나오며 0이 아닌 코드로 끝난다.
  - 접근: 첫 글자 `[a-z0-9]`, 이후 `[a-z0-9_-]`, 길이 1–32 규칙을 순수 함수로 두고, 형식 위반과
    예약 이름을 서로 다른 sentinel로 구분한다. 이 검증을 파일시스템·등록 파일 접근보다 먼저
    수행해 거부 경로가 디스크에 전혀 닿지 않게 한다.
  - 검증 조건:
    - 결과: 목적과 동일. 두 경우 모두 종료 코드가 2이고, 형식 위반 메시지에는 허용 형식이
      한 줄로 들어가며 예약 이름 메시지에는 그 이름이 예약되어 있음이 들어간다.
    - 확인: 대문자 포함, 공백 포함, 경로 구분자 포함, `..`, 빈 문자열, 33자, `-`로 시작하는
      이름과 `default`를 각각 넣어 종료 코드와 stderr 내용을 확인하는 테스트. `-`로 시작하는
      이름은 SPEC §3의 POSIX 관례에 따라 `--` 뒤에 두고 확인한다. 각 케이스에서 홈 아래에
      디렉토리가 생기지 않고 등록 파일이 새로 만들어지지도 변경되지도 않음을 함께 확인하며,
      등록 파일이 이미 있는 상태에서 거부되는 경우도 포함해 그 내용이 바뀌지 않음을 확인한다.
      이름 검증 함수 자체는 경로 기준값 없이 도는 순수 함수 테스트로도 덮는다.
  - 참조: SPEC §5.2, §5.3 / ANALYSIS §3, §5 D3, D7, D12

- [x] task-004: `add`가 이미 등록된 이름과 점유된 경로에서 기존 상태를 그대로 두고 실패한다
  - 목적: 이미 등록된 이름으로 `add`를 실행하면 기존 프로필의 디렉토리와 등록 내용이 바뀌지
    않고, 프로필 디렉토리가 놓일 자리에 비어 있지 않은 디렉토리가 있으면 그 내용을 건드리지
    않고 실패하며, 두 경우 모두 상황과 사용자가 취할 수 있는 조치가 stderr에 나온다.
  - 접근: 등록 여부를 대상 경로 조사보다 먼저 확인해 등록 충돌이 파일시스템에 닿기 전에
    끝나게 한다. 대상 자리가 비어 있지 않은 디렉토리이거나 디렉토리가 아니면 안을 읽지도
    지우지도 않고 sentinel로 실패하며, CLI가 그 경로와 조치를 메시지에 함께 싣는다. 등록
    파일이 손상된 경우에는 빈 목록으로 진행하지 않고 파일 경로를 알리며 멈춘다.
  - 검증 조건:
    - 결과: 목적과 동일. 이미 등록된 이름은 종료 코드 4, 점유된 경로는 종료 코드 5, 손상된
      등록 파일은 종료 코드 1이며, 세 경우 모두 등록 파일 내용이 실행 전후로 동일하다.
    - 확인: (1) 같은 이름으로 두 번 `add` → 두 번째가 종료 코드 4이고 기존 디렉토리 내용과
      등록 파일 바이트가 그대로. (2) 대상 경로에 파일이 하나 든 디렉토리를 미리 만들고 `add`
      → 종료 코드 5, stderr에 그 경로가 나오고 안의 파일이 그대로. (3) 대상 경로에 같은
      이름의 파일을 놓고 `add` → 실패하고 그 파일이 그대로. (4) 손상된 등록 파일로 `add`
      → 종료 코드 1이고 파일 내용이 덮어써지지 않음.
  - 참조: SPEC §5.4, §5.5, §5.11 / ANALYSIS §2, §3, §5 D11, D12, D14

- [x] task-005: `rm`이 확인을 거친 뒤 프로필 디렉토리와 등록을 함께 지운다
  - 목적: `ccswitch rm <name>`은 사용자가 삭제 의도를 확인하기 전에는 디렉토리와 등록 항목
    어느 쪽도 지우지 않고, 확인했거나 확인 생략을 명시하면 둘이 함께 사라져 이어서 실행한
    `list` 출력에 그 이름이 나타나지 않는다.
  - 접근: 삭제 대상 이름과 실제 경로를 보여주는 프롬프트를 기본으로 하고 `y`/`yes`만 승인으로
    본다. `--yes`/`-y`가 있으면 프롬프트 없이 진행하고, 표준 입력이 대화형이 아니면서 플래그도
    없으면 아무것도 지우지 않고 그 플래그를 안내하며 실패한다. 승인 후에는 디렉토리를 먼저
    지우고 등록을 나중에 지운다. 대화형 여부와 입력·출력 스트림은 진입점이 실제 표준 입력에서
    판정해 CLI 경계에 값으로 넘기므로, 테스트가 세 갈래를 모두 구성할 수 있다.
  - 검증 조건:
    - 결과: 목적과 동일. 사용자가 프롬프트에서 취소하면 오류가 아니라 종료 코드 0으로 끝나되
      취소했음이 stderr에 남는다. 비대화형에서 플래그가 없으면 종료 코드 2로 끝난다.
    - 확인: (1) `--yes`로 삭제 → 디렉토리와 등록이 모두 사라지고 `list`에 그 이름이 없으며
      종료 코드 0. (2) 대화형으로 구성하고 `n`과 빈 입력을 각각 넣음 → 디렉토리와 등록이
      모두 그대로이고 종료 코드 0, stderr에 취소 표시. (3) 대화형으로 구성하고 `y` 입력 →
      삭제 성공. (4) 비대화형에 플래그 없음 → 디렉토리와 등록 그대로, 종료 코드 2, stderr에
      생략 플래그 안내. (5) 손상된 등록 파일 → 아무것도 지우지 않고 파일 경로를 알리며 실패.
      (6) 프로필 디렉토리 안에 파일과 하위 디렉토리를 만들어 둔 상태에서 삭제가 완료되고,
      홈 아래의 다른 프로필 디렉토리와 기본 설정 디렉토리는 그대로 남는다.
  - 참조: SPEC §5.7, §5.8, §5.11 / ANALYSIS §2, §3, §5 D13, D14, D15

- [x] task-006: `rm`이 예약 이름과 등록되지 않은 이름을 거부한다
  - 목적: `ccswitch rm default`는 거부되고 Claude Code의 기본 설정 디렉토리가 그대로 남으며,
    등록되지 않은 이름으로 `rm`을 실행하면 그 이름을 찾을 수 없다는 내용이 stderr에 나오고
    0이 아닌 코드로 끝난다.
  - 접근: 예약 이름 검사를 등록 파일을 읽기 전 가장 먼저 하고, 그다음 이름 형식, 그다음 등록
    여부를 본다. 세 갈래 모두 프롬프트와 삭제에 도달하지 않는다.
  - 검증 조건:
    - 결과: 목적과 동일. 예약 이름과 형식 위반은 종료 코드 2, 등록되지 않은 이름은 종료
      코드 3이다.
    - 확인: (1) 기본 설정 디렉토리에 파일을 넣어 둔 상태에서 `rm default`와 `rm default --yes`
      가 모두 종료 코드 2로 끝나고 그 디렉토리와 안의 파일이 그대로임을 확인. (2) 등록되지
      않은 이름으로 `rm` → 종료 코드 3, stderr에 찾을 수 없다는 내용, 홈 아래 어떤 디렉토리도
      사라지지 않음. (3) 규칙 위반 이름으로 `rm` → 종료 코드 2. 모든 케이스에서 프롬프트가
      출력되지 않는다.
  - 참조: SPEC §5.9, §5.10 / ANALYSIS §2, §3, §5 D3, D7, D12
