# profile-auth

## 1. 범위

프로필 단위 인증을 다룬다 — 프로필을 지정한 로그인·로그아웃, 삭제 시 자격증명 정리, 프로필별
계정 정보 조회.

다루는 영역은 다음과 같다.

- Claude Code 세션을 띄우지 않고 프로필별로 로그인·로그아웃하는 것
- 프로필을 지울 때 자격증명 정리를 Claude Code에 위임하는 것
- 프로필별 계정 정보를 조회해 목록에 보여주는 것
- 위 동작들의 성공·실패 출력과 종료 코드

### 입력 맥락

- profile-store와 profile-launcher가 완료되어 `add`·`list`·`rm`·`use`가 동작한다. 프로필의
  존재·위치·이름 기준은 profile-store가, `CLAUDE_CONFIG_DIR` 주입과 프로세스 실행 방식은
  profile-launcher가 소유하며 이 feature는 그 위에 얹는다.
- 확인한 동작 (Claude Code 2.1.220, Windows):
  - `claude auth`에 `login`·`logout`·`status` 하위 명령이 있다. `login`은 `--claudeai`(기본),
    `--console`, `--email <email>`, `--sso` 옵션을 갖는다.
  - `claude auth status`는 JSON이 기본 출력이고 `--text`로 사람이 읽는 형태를 낼 수 있다.
    JSON 필드는 `loggedIn`, `authMethod`, `apiProvider`, `email`, `orgId`, `orgName`,
    `subscriptionType`이다.
  - Windows 자격증명은 설정 디렉토리 안 `.credentials.json`이고, macOS는 Keychain 서비스
    이름에 `CLAUDE_CONFIG_DIR` 경로 문자열의 `sha256[:8]`을 붙인다.
- `/spec-init` 전 논의에서 정한 방향:
  - 계정 정보를 설정 디렉토리 안 파일 파싱으로 읽지 않고 `claude auth status`의 구조화된
    출력에 맡긴다. ROADMAP M2가 계정 정보 표시를 이 단계에 묶은 근거는 "비공식 내부 파일
    포맷에 의존해야 한다"였는데 그 전제가 사실과 다르다. 묶는 이유는 같은 `claude auth`
    표면을 쓴다는 것으로 바뀌며, 묶는 결론 자체는 유효하다.
  - 구독 계정 로그인은 브라우저 OAuth를 거치므로 ccswitch가 없앨 수 없다. 브라우저에 다른
    계정이 이미 붙어 있으면 그 계정으로 인증이 통과할 수 있다는 주의는 README에 있다.
  - 검토했으나 접은 접근: `list`가 항상 계정 정보를 조회하는 방식. 프로필마다 부프로세스가
    떠서 목록 조회가 눈에 띄게 느려지고, 로그인되지 않은 프로필이 섞여 있으면 볼 것도 없는
    항목 때문에 매번 그 지연을 치른다.

## 2. 목표

계정을 프로필에 붙이고 떼는 일을 ccswitch 안에서 끝낸다.

지금은 새 프로필을 `use`로 띄운 뒤 그 세션 안에서 로그인해야 하고, 어느 프로필이 어느 계정인지
알려면 세션을 열어 봐야 한다. 이 feature 뒤에는 로그인·로그아웃·계정 확인이 각각 명령 한 줄이
되고, 프로필을 지울 때 자격증명이 함께 정리된다.

## 3. 제약

- Windows에서 동작해야 한다. macOS 실기 검증은 이후 마일스톤이다.
- Go로 구현한다.
- 관리자 권한을 요구하지 않는다.
- 자격증명을 직접 만들거나 읽거나 지우지 않는다. 로그인·로그아웃·상태 조회를 모두 Claude
  Code에 위임하고, ccswitch는 어느 설정 디렉토리를 보게 할지만 정한다.
- 계정 정보는 Claude Code가 주는 구조화된 출력에서 읽는다. 설정 디렉토리 안의 파일을 직접
  파싱하지 않는다.
- 프로필 지정과 환경 주입 방식은 profile-launcher가 정한 것을 그대로 쓴다 — 같은 프로필에
  대해 항상 같은 경로 문자열, `default`는 주입 대신 제거, 인증 관련 환경변수 제거. `default`도
  `use`와 같게 대상 이름으로 받는다.
- 구독 계정 로그인은 브라우저를 거치며, 이 feature가 그 단계를 없애지 않는다.
- 삭제는 되돌릴 수 없다. 자격증명 정리가 실패한 상태로 조용히 지우지 않는다.
- 계정 정보 조회는 프로필당 부프로세스를 하나 띄우는 비용이 있으므로 기본 목록 출력에 넣지
  않는다.
- 기존 명령의 출력과 종료 코드 계약을 깨지 않는다. 새 실패 원인은 새 종료 코드로 구분한다.

## 4. 제외 범위

- 설정 자산 공유와 링크 구성 (shared-assets)
- 기존 기본 설정 디렉토리를 이름 있는 프로필로 승격하는 것 (profile-import)
- 브라우저 계정 선택을 도구가 대신하는 것. 시크릿 창 자동 실행이나 브라우저 프로필 지정은
  범위 밖이며, 사용자가 브라우저에서 계정을 고른다
- API 키·콘솔 인증 흐름을 ccswitch가 따로 설계하는 것. `claude auth login`이 이미 주는 옵션을
  그대로 넘길 수 있으면 그것으로 충분하다
- 장기 토큰 발급(`claude setup-token`) 연동
- 계정 정보 캐시. 조회할 때마다 Claude Code에 묻는다
- 기계 판독용 출력 형식(JSON 등). 이번 출력도 사람이 읽는 형태만 낸다
- 여러 프로필을 한 번에 로그아웃하거나 정리하는 일괄 동작
- macOS·Linux에서의 실기 검증 (macos-support). 삭제 후 재생성 시 이전 계정으로 인증되지
  않는다는 서비스 완료 기준 3의 macOS 관찰은 M4가 소유한다

## 5. 완료 조건

1. `ccswitch login <name>`이 Claude Code 대화형 세션을 띄우지 않고 그 프로필의 로그인 절차를
   시작하며, 절차를 마친 뒤 그 프로필로 조회한 인증 상태가 로그인된 것으로 나온다.
2. `ccswitch logout <name>`이 그 프로필의 로그아웃을 마치고, 이어서 조회한 인증 상태가
   로그인되지 않은 것으로 나온다.
3. 이름 있는 프로필에 `login`·`logout`을 실행해도 기본 설정 디렉토리의 인증 상태와 다른
   프로필의 인증 상태가 바뀌지 않는다.
4. 등록되지 않은 이름, 디렉토리를 쓸 수 없는 프로필, PATH에서 실행 파일을 찾을 수 없는
   경우에 `login`·`logout`이 `use`와 같은 내용으로 거부되고 종료 코드도 같다.
5. 계정 정보를 요청하는 옵션을 준 `ccswitch list`가 프로필별로 계정 식별 정보와 플랜을
   보여주고, 로그인되지 않은 프로필은 그 사실을 구별할 수 있게 표시한다.
6. 옵션 없는 `ccswitch list`의 출력이 이 feature 전후로 같고, 계정 조회를 위한 프로세스가
   실행되지 않는다.
7. `ccswitch rm <name>`이 프로필 디렉토리를 지우기 전에 그 프로필의 자격증명 정리를 Claude
   Code에 위임한다.
8. 자격증명 정리가 실패하면 `rm`이 디렉토리와 등록 어느 쪽도 지우지 않고, stderr에 실패
   이유가 표시되며 종료 코드가 0이 아니다.
9. 정리를 건너뛰고 지우는 명시적 수단이 있으며, 그것을 썼을 때 자격증명이 남을 수 있다는
   것이 사용자에게 표시된다.
10. 로그인되지 않은 프로필에 `rm`을 실행해도 정리 실패로 막히지 않고 삭제가 끝난다.
11. `login`·`logout`·계정 조회가 실패했을 때 stderr에 무엇이 실패했는지와 사용자가 취할 수
    있는 조치가 표시되고 종료 코드가 0이 아니다.
12. README의 상태 문구와 사용 절차가 실제 동작과 일치한다 — `login`·`logout`으로 계정을 붙이고
    뗄 수 있다는 것과 `list`가 계정을 보여줄 수 있다는 것, 그리고 그 사용법이 적혀 있고, 아직
    없는 명령을 쓸 수 있는 것처럼 적지 않는다.
